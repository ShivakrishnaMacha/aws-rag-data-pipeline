# RAG Data Pipeline — AWS-Native Document Ingestion & Hybrid Retrieval

![Python](https://img.shields.io/badge/python-3.12-blue)
![FAISS](https://img.shields.io/badge/vector%20search-FAISS-orange)
![Streamlit](https://img.shields.io/badge/demo-Streamlit-red)
![License](https://img.shields.io/badge/license-MIT-green)

A production-style **RAG data pipeline** built the way a data engineer would build it:
the pipeline is the star, the LLM is a pluggable adapter. Documents land in an
S3-style raw zone, get validated, deduped, chunked, embedded and indexed by an
idempotent ETL pipeline, then served through a **hybrid BM25 + dense retrieval
API** with citation-grounded answers — plus an eval harness that keeps
retrieval quality honest.

> 🎬 **Live demo:** <live-demo-url>

## Architecture

```mermaid
flowchart LR
    A[Raw docs<br/>S3 raw zone] --> B[ingest.py<br/>validate · dedupe · manifest]
    B --> C[chunk.py<br/>recursive chunking + overlap]
    C --> D[embed.py<br/>MiniLM-L6-v2 · batched · cached]
    D --> E[index.py<br/>FAISS dense index<br/>DuckDB metadata]
    E --> F[search.py<br/>hybrid BM25 + dense fusion]
    F --> G[answer.py<br/>extractive, citation-grounded]
    G --> H[app.py<br/>Streamlit chat UI]
    E --> I[evaluate.py<br/>recall@k · MRR · citations]
```

## Features

- **S3 zone pattern** — `s3_mock/raw-zone` and `s3_mock/processed-zone` mirror the
  real `s3://<bucket>/raw/` and `s3://<bucket>/processed/` layout; swap the local
  helpers for `boto3` to go live (paths are identical).
- **Idempotent pipeline** — content-hash manifest skips unchanged docs; embedding
  cache never re-embeds unchanged chunks.
- **Semantic-ish chunking** — recursive character chunking with 120-char overlap,
  section-aware metadata (`doc_id#section#n`), char offsets per chunk.
- **Hybrid retrieval** — BM25 (lexical) + FAISS cosine (dense), min-max normalized
  and fused (α=0.6 dense). Beats either channel alone on mixed query styles.
- **Grounded answers** — extractive composer cites `[doc_id]` for every answer;
  a `LLMAdapter` seam documents the Bedrock Converse API production path.
- **Eval harness** — 40-question synthetic QA set; reports recall@k, MRR,
  citation accuracy and p50 latency.

## Quickstart

```bash
pip install -r requirements.txt

# 1. Generate the seeded synthetic corpus (~300 ops runbooks)
python data/generate_corpus.py

# 2. Run the pipeline: ingest -> chunk -> embed -> index
python pipeline/run.py

# 3. Ask questions
python -c "
from retrieval.search import HybridRetriever
from retrieval.answer import compose_answer
r = HybridRetriever()
print(compose_answer(r.search('How do I fix Kafka consumer lag?'))['answer'])
"

# 4. Evaluate retrieval quality
python eval/evaluate.py   # writes eval/report.md

# 5. Launch the chat demo
streamlit run app.py
```

> ⏳ First run downloads the `all-MiniLM-L6-v2` model (~90 MB) and embeds the
> corpus — expect a few minutes. Subsequent runs are incremental and fast.
> On Streamlit Community Cloud the app builds the corpus + index automatically
> on first launch (one-time ~3-5 min cold start).

## Project structure

```
├── app.py                  # Streamlit chat UI (query -> answer + citations + latency)
├── data/
│   └── generate_corpus.py  # seeded synthetic corpus: 300 data-eng ops runbooks
├── pipeline/
│   ├── ingest.py           # raw zone -> validation, dedupe (sha256), manifest
│   ├── chunk.py            # recursive chunking w/ overlap + metadata
│   ├── embed.py            # batched MiniLM embeddings + disk cache
│   ├── index.py            # FAISS index + DuckDB chunk metadata
│   └── run.py              # orchestrator (idempotent)
├── retrieval/
│   ├── search.py           # hybrid BM25 + dense retrieval, score fusion
│   └── answer.py           # extractive grounded answers + Bedrock adapter stub
├── eval/
│   ├── evaluate.py         # recall@k, MRR, citation accuracy -> report.md
│   └── eval_qa.json        # 40 synthetic QA pairs (generated)
├── tests/                  # pytest: chunking overlap, dedupe, fusion scoring
├── s3_mock/                # local stand-ins for S3 raw/processed zones
├── requirements.txt
└── Dockerfile
```

## Production extensions

- **Amazon Bedrock Knowledge Bases** — replace the local FAISS index with a
  managed knowledge base; keep `retrieval/search.py` as the query interface.
- **OpenSearch Serverless vs FAISS-on-S3** — FAISS-on-S3 is cheap and simple for
  <10M vectors; OpenSearch Serverless wins when you need managed scaling,
  filtering and hybrid search in one query.
- **DynamoDB metadata** — the DuckDB `chunks` table maps 1:1 to a DynamoDB table
  with `chunk_id` as partition key (pay-per-request, same access pattern).
- **SageMaker async embedding** — move `embed.py` batching to a SageMaker async
  endpoint for GPU throughput at scale.
- **Incremental re-indexing** — watch the raw zone (S3 Event Notifications →
  SQS) and re-run only changed docs; the manifest + embedding cache already
  support this.
- **Bedrock Converse API** — `retrieval/answer.py` documents a drop-in
  `BedrockLLMAdapter` for generative answers grounded on retrieved chunks.
